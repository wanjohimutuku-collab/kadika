# Security review, October 2026

- **Date:** 2026-10-21
- **Commit reviewed:** `8287d6b` (`main`, after PR #34 staff routes and PR #32 CI/release pipeline; production runs v0.4.3)
- **Type:** static review only. No active testing, scanning or exploitation of `kadisasa.com`, `api.`, `my.` or `coolify.` was done.
- **Scope:** `apps/api` (auth, staff `/v1/ops/*`, guest card, webhooks, settings secrets), `apps/web` (headers, middleware, light card, token storage), `packages/*` (crypto, payments, messaging, schemas), `.github/workflows/`, `infra/docker/`, `docker-compose.coolify.yml` (read only; PR #35 owns changes to it).
- **Tools:** `pnpm audit` (lockfile), a regex secrets scan over the full git history (162 commits; gitleaks/semgrep/trivy were not installed on the review machine), manual code review.

## Executive summary

The core security design holds up. Card tokens are 128-bit, stored only as SHA-256 hashes and looked up by hash; QR codes are Ed25519-signed; event signing keys and provider settings are AES-256-GCM encrypted with `KEY_ENC_SECRET`; refresh tokens rotate with reuse detection; every authenticated request re-reads the user's status, so a suspension takes effect at once and suspended users cannot sign in or refresh. Every `/v1/ops/*` route added in PR #34 goes through `requireStaff` with the right level, phone reveal requires a written reason of at least 5 characters and is audit-logged before the number is returned, and payment webhooks are HMAC-verified and applied at most once per reference.

The one **High** finding is that the **staff second factor exists only in the mock client**: the real API never asks for it, so staff sign in to `my.kadisasa.com` with an SMS code alone (H-01). That is the account class that can read every customer, reveal phone numbers and change SMS/payment provider settings. The main **Medium** risks are SMS-cost abuse through an unthrottled OTP endpoint (M-01), rate limiting keyed on a client-controlled `X-Forwarded-For` value (M-03), no Content-Security-Policy on the web app (M-04) combined with 30-day refresh tokens in `localStorage` (M-05), a gate-PIN lockout that parallel requests can outrun (M-06), and a stored XSS through a `javascript:` venue map link on guest cards (M-02, **fixed in this PR**).

No Critical findings. No secrets were found in git history.

## Detailed findings

### H-01 — Staff second factor is not implemented in the API

- **Severity:** High (CVSS 7.4, `AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:N`)
- **Location:** `apps/api/src/auth/service.ts:45` (`verifyOtp` issues full tokens to staff), `packages/api-client/src/http-repository.ts` (no `verifyStaffSecondFactor`), `apps/web/src/components/public/login.tsx:156` (UI branch only reached in mock mode), `packages/api-client/src/mock/mock-repository.ts:132` (mock code `654321`)
- **Description:** CLAUDE.md §17.8 and ADR 012 say staff "sign in with a second factor". The web login has a second-factor screen and an e2e test for it, but both run only against the mock repository. The API never returns `needsSecondFactor`, has no second-factor endpoint, and `verifyOtp` returns a full access and refresh token to any `role_global = admin` user after the SMS code.
- **Impact:** Anyone who can receive a staff member's SMS (SIM swap, SS7 interception, a lost phone, an SMS-forwarding app) gets the staff panel: every customer and wedding, support lookup across all guests, phone reveal, account suspension, PDPA deletion, and (admin level) the SMS, WhatsApp and payment gateway settings. The passing e2e test gives false assurance that the control exists.
- **Remediation:** Add TOTP for staff: `POST /v1/auth/staff/totp/verify`, a `staff_totp_secret` column encrypted with `KEY_ENC_SECRET`, enrolment from `/ops`, and have `verifyOtp` return a short-lived, second-factor-only token (not an access token) when the user is staff. `requireStaff` and `requireSettingsAdmin` should then require an `amr`/`mfa` claim in the access token. Until then, keep the number of staff accounts minimal and on carriers with SIM-swap protection.
- **References:** CWE-308, OWASP ASVS V2.8.

### M-01 — OTP request has no per-client or global cap (SMS pumping)

- **Severity:** Medium (CVSS 6.5, `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`; the "availability" here is money)
- **Location:** `apps/api/src/app.ts:257`, `apps/api/src/auth/otp.ts:27`
- **Description:** `POST /v1/auth/otp/request` is limited only per phone number (one per 30 s, five per hour). There is no limit per client and no global ceiling, and the counters live in an in-process `Map` (lost on restart, not shared between instances, never pruned).
- **Impact:** An attacker cycling through valid Tanzanian or Kenyan numbers can make the API send unlimited SMS, billed to Kadi Sasa (classic SMS pumping / toll fraud), and can grow the OTP map without bound.
- **Remediation:** Add a `RateLimiter` per client on this route (after M-03 is fixed so the client key is real), a global hourly SMS budget with an alert, and move OTP state to the shared `RateStore`/Redis with a TTL. Consider a per-prefix limit for premium or unusual ranges.
- **References:** CWE-770, OWASP API4:2023.

### M-02 — Stored XSS: `javascript:` venue map link on the guest card (fixed)

- **Severity:** Medium (CVSS 5.4, `AV:N/AC:L/PR:L/UI:R/S:C/C:L/I:L/A:N`)
- **Location:** `apps/api/src/app.ts:74` (was `z.string().url()`), `apps/web/src/lib/light-card/render.ts:310`, `packages/schemas/src/domain.ts:197`
- **Description:** zod 3's `.url()` only checks that `new URL()` parses, so `javascript:…` and `data:…` were accepted as `venueMapUrl`. The light card escapes HTML but put the value straight into `href`, so any organiser (or committee member) could put a script link on every guest card at `kadisasa.com/c/<token>`.
- **Impact:** Script on the trusted card domain when a guest taps "Fungua ramani": a convincing fake pay flow, reading the card token, and undermining the P1/P7 trust promise.
- **Remediation (done):** the API and the shared form schema now accept only `http(s)` links, and the renderer ignores any stored value that is not `http(s)` and falls back to the OpenStreetMap search. Tests added in `apps/api/src/phase1.test.ts` and `apps/web/src/lib/light-card/render.test.ts`. Existing rows are neutralised by the renderer, so no migration is needed.
- **References:** CWE-79, CWE-83.

### M-03 — Rate limits keyed on the first `X-Forwarded-For` entry

- **Severity:** Medium (CVSS 5.3, `AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:L/A:N`)
- **Location:** `apps/api/src/app.ts:198`, `apps/api/src/rate-limit.ts:25`
- **Description:** `client()` takes the **leftmost** `X-Forwarded-For` value. Production sits behind Cloudflare and Coolify's Traefik. Cloudflare passes a client-supplied `X-Forwarded-For` through and appends the real address, so the leftmost entry is attacker-controlled whenever Traefik trusts the incoming header; if Traefik does not trust Cloudflare's addresses, every visitor instead shares a few Cloudflare edge IPs. Separately, the in-memory store clears **all** counters once 50,000 keys exist, which spoofed keys reach quickly.
- **Impact:** The per-IP limits on card reads, RSVP, pay starts, payment-status reads and gate joins can be bypassed (or, in the other configuration, legitimate guests at one venue throttle each other). This amplifies M-01 and M-06.
- **Remediation:** Use `CF-Connecting-IP` when the request comes from a Cloudflare range (or configure Traefik `forwardedHeaders.trustedIPs` to Cloudflare's ranges and take the **rightmost untrusted** hop), and make the trusted-proxy setting explicit config. Evict expired keys instead of clearing the whole map. Verify the actual header values in staging before relying on any per-IP limit.
- **References:** CWE-348, CWE-307.

### M-04 — No Content-Security-Policy on the web app

- **Severity:** Medium (CVSS 5.0, `AV:N/AC:H/PR:N/UI:R/S:C/C:L/I:L/A:N`)
- **Location:** `apps/web/next.config.ts:7`
- **Description:** The web app sets `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` and `Permissions-Policy`, but no CSP, on the public site, the guest card, the organizer console (`app.`) and the staff panel (`my.`). (The API's own responses do have a strict CSP.)
- **Impact:** Any XSS (M-02 was one) runs unrestricted, and with M-05 can take over organizer and staff sessions.
- **Remediation:** Add a nonce-based CSP in middleware for the console and `/ops` (`default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; connect-src 'self' <API origin>; img-src 'self' data: <API origin>; frame-ancestors 'none'; base-uri 'none'; object-src 'none'`). For the light card, hash its single inline script (`script-src 'sha256-…'`). Roll out with `Content-Security-Policy-Report-Only` first.
- **References:** OWASP Secure Headers, CWE-1021.

### M-05 — Access and 30-day refresh tokens stored in `localStorage`

- **Severity:** Medium (CVSS 4.8, `AV:N/AC:H/PR:N/UI:R/S:U/C:H/I:L/A:N`)
- **Location:** `packages/api-client/src/http-repository.ts:57`, `apps/web/src/lib/repo.ts:54`, `packages/api-client/src/http-repository.ts` (`REFRESH_TTL_MS` 30 days in `apps/api/src/auth/tokens.ts:7`)
- **Description:** The console and the staff panel keep both tokens in `localStorage` under `harusi.auth.v1`.
- **Impact:** Any script running on `app.` or `my.` (XSS, a compromised dependency) can read a 30-day refresh token, including a staff one, and keep using it from elsewhere until reuse is detected.
- **Remediation:** Keep the access token in memory only and move the refresh token to an `HttpOnly; Secure; SameSite=Strict` cookie scoped to the API host and `/v1/auth/refresh` (needs `credentials: 'include'` and a CORS `allowCredentials` for the console origins). Shorter refresh lifetime for staff (for example 12 hours). Mobile keeps using secure storage.
- **References:** CWE-922, OWASP ASVS V3.

### M-06 — Gate PIN lockout counter is not atomic

- **Severity:** Medium (CVSS 5.3, `AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:N/A:N`)
- **Location:** `apps/api/src/services/gate.ts:146`
- **Description:** `join` reads `failedAttempts`, compares the PIN, then writes `attempts + 1`. Requests sent in parallel all read the same count, so a burst of guesses is counted as one attempt and the 5-attempt lock is outrun. The gate link code is needed first, but it travels in WhatsApp/SMS to gate agents.
- **Impact:** With a leaked gate link, a 4–6 digit PIN can be brute-forced faster than intended (also helped by M-03), giving the gate bundle: guest names, short codes, party sizes and last 4 phone digits for the event.
- **Remediation:** Reserve the attempt before checking: `UPDATE gate_links SET failed_attempts = failed_attempts + 1 WHERE id = $1 AND (locked_until IS NULL OR locked_until <= now()) RETURNING failed_attempts`; refuse if no row or the count is over the limit; reset on success. Consider 6-digit minimum PINs.
- **References:** CWE-362, CWE-307.

### L-01 — Refresh-token rotation race

- **Severity:** Low (CVSS 3.7)
- **Location:** `apps/api/src/auth/service.ts:122`
- **Description:** `refresh` reads the row, checks `revokedAt`, then marks it spent without a condition, so two concurrent uses of one refresh token both succeed and neither triggers reuse detection.
- **Impact:** A stolen refresh token used at the same moment as the real client is not detected.
- **Remediation:** Spend it with `UPDATE … WHERE id = $1 AND revoked_at IS NULL RETURNING id`. Not changed in this PR because the losing request would get a 401, and the web client shares tokens across tabs through `localStorage`: the client must first serialise refreshes (one in flight, others wait for it) or it would sign users out.

### L-02 — Snippe webhook accepted future timestamps (fixed)

- **Severity:** Low (CVSS 3.1)
- **Location:** `packages/payments/src/snippe.ts:189`
- **Description:** The replay window checked only `now - ts > 300`, so a signed callback with a far-future timestamp would stay valid until then.
- **Impact:** Limited (the HMAC key is still needed and outcomes are idempotent), but the replay protection was one-sided.
- **Remediation (done):** compare `Math.abs(now - ts)`; test added.

### L-03 — Africa's Talking webhook secret in the query string

- **Severity:** Low (CVSS 3.1)
- **Location:** `apps/api/src/app.ts:406`
- **Description:** The API's own request log records only the route pattern, but Cloudflare and Traefik access logs record full URLs, including `?secret=…`.
- **Impact:** Anyone with access to proxy logs can forge delivery reports (status changes only).
- **Remediation:** Use a separate, per-provider secret for this callback (not the shared `WEBHOOK_SECRET` that also protects the Evolution and NextSMS hooks), make sure Traefik access logs are off or strip query strings, and rotate it if logs were ever shipped elsewhere.

### L-04 — A saved provider secret follows a changed `baseUrl`

- **Severity:** Low (CVSS 3.8, admin staff only)
- **Location:** `apps/api/src/services/messaging-settings.ts:350`, `apps/api/src/services/payment-settings.ts:208`
- **Description:** On save, an empty secret field keeps the stored secret when the provider name is unchanged, even if `baseUrl` now points somewhere else. "Send test" then delivers the API key to that host.
- **Impact:** A compromised admin-staff session (see H-01, M-05) can exfiltrate the WhatsApp/Evolution/Africa's Talking keys without ever seeing them in the UI.
- **Remediation:** If `baseUrl` (or any non-secret endpoint field) changes, require the secrets to be re-entered.

### L-05 — OTP lockout per phone lets anyone lock a user out

- **Severity:** Low (CVSS 3.1)
- **Location:** `apps/api/src/auth/otp.ts:95`
- **Description:** Five wrong codes for a phone number lock that number for 10 minutes, and anyone can submit codes for any number.
- **Impact:** Targeted denial of sign-in (for example an organizer on the wedding day, or a gate committee member).
- **Remediation:** Count failures per (phone, client) as well, and let a fresh, successfully delivered code clear the lock for the owner of the phone.

### L-06 — Workflows used the default token permissions (fixed)

- **Severity:** Low (CVSS 2.6)
- **Location:** `.github/workflows/ci.yml`, `.github/workflows/mobile-eas.yml`
- **Description:** Neither workflow declared `permissions`, so `GITHUB_TOKEN` got the repository default, which may be read/write.
- **Remediation (done):** both now declare `permissions: contents: read`. `build-push.yml` already scopes per job.

### L-07 — Third-party GitHub Actions pinned by tag

- **Severity:** Low (CVSS 3.1)
- **Location:** `.github/workflows/build-push.yml:111–148, 229` (`docker/*`), `.github/workflows/ci.yml` (`pnpm/action-setup@v4`)
- **Description:** The `docker/*` actions run in jobs with `packages: write` and, for `deploy`, `contents: write`. A moved tag would run new code with those rights.
- **Remediation:** Pin third-party actions to full commit SHAs (keep the tag in a comment) and let Dependabot update them. Also make sure the `production` environment has a required reviewer, since `deploy` force-pushes `deploy/production`.

### L-08 — `.dockerignore` did not exclude `.deploy.env` (fixed)

- **Severity:** Low (CVSS 3.1)
- **Location:** `.dockerignore`
- **Description:** `scripts/deploy.sh` reads `.deploy.env` (GHCR token) from the repo root and builds with `COPY . .`. The final images copy only build outputs, but the file sat in the local builder's cache layers.
- **Remediation (done):** `.deploy.env`, `.docker-cache` and `.claude` are now in `.dockerignore`.

### L-09 — Web app sent no HSTS header (partly fixed)

- **Severity:** Low (CVSS 2.4)
- **Location:** `apps/web/next.config.ts:7`
- **Description:** The API sends HSTS; the web app did not.
- **Remediation (done):** `Strict-Transport-Security: max-age=31536000` on all web responses. `includeSubDomains` and preload were left out on purpose because other names under the domain (mail, Coolify) are outside this app; add them once every subdomain is confirmed HTTPS-only.

### L-10 — Dependency advisories, all dev or build time

- **Severity:** Low (CVSS 2.5 in this context)
- **Location:** `pnpm-lock.yaml`
- **Description:** `pnpm audit` reports 37 advisories: 2 critical, 13 high, 19 moderate, 3 low. Tracing each high/critical one, none ships in the API or web runtime images:
  - `tinypool` ≤ 2.1.1 (critical, prototype-pollution gadget): via `vitest` (tests only).
  - `node-forge` 1.4.0, `image-size` 1.2.1, `extract-zip`, `basic-ftp`, `tmp`: via `@expo/cli`, `metro`, `@puppeteer/browsers`, `get-uri` (mobile tooling, Lighthouse/Playwright).

### I-01 — SVG logo validator is a denylist

- **Location:** `packages/schemas/src/branding.ts:116`
- **Notes:** Regex denylists for SVG can be bypassed in principle. Here the risk is accepted: only admin staff upload, the logo is served with `Content-Security-Policy: default-src 'none'; sandbox`, `nosniff`, and shown only through `<img>`. Keep those headers if the route ever changes.

### I-02 — Git history secrets scan: clean

- **Notes:** All 162 commits on every branch were scanned for private keys, AWS/GitHub/Slack/Google/Meta tokens and `*_SECRET|TOKEN|PASSWORD|API_KEY = <16+ chars>` assignments, and for committed `.env`, `.pem`, `.key` files. Only test fixtures turned up (`env-password-9999`, an all-zero `KEY_ENC_SECRET`, `a-long-enough-secret`). Phone numbers in history are synthetic test numbers. A regex scan is weaker than gitleaks; add `gitleaks/gitleaks-action` to CI for ongoing coverage.

### I-03 — Fake providers keep unbounded in-memory lists

- **Location:** `packages/payments/src/index.ts:85` (`FakePaymentProvider.started`), `apps/api/src/index.ts:46`
- **Notes:** Production still constructs `FakePaymentProvider` when `PAYMENT_PROVIDER=fake` and a webhook secret is set, and its `started` array grows forever. Not exploitable for money (completing a payment still needs a signed webhook), but it is a slow memory leak; refuse `fake` providers when `NODE_ENV=production` once Snippe is live.

## What was checked and found sound

- **Staff routes (PR #34):** every `/v1/ops/*` handler calls `requireStaff` with the documented level (`lookup`, `reveal`, `suspend`, `plan`, `requests`; reads for all staff); settings and branding writes call `requireSettingsAdmin`. Suspended or non-admin users are refused. Staff accounts cannot be suspended from the panel.
- **Phone reveal:** reason trimmed and ≥ 5 characters, audit row written before the number is returned, lookups audit-logged with digits scrubbed.
- **Suspension:** checked on OTP verify, on refresh, and on every authenticated request; suspension revokes all refresh tokens in the same transaction. Deletion wipes name and phone and revokes sessions.
- **JWT:** HS256 pinned in `jwtVerify`; gate tokens and user tokens cannot be swapped (gate tokens have no `sub`, user tokens fail the `typ` check); gate tokens are re-checked against link revocation and expiry on every call. Production refuses `change-me` secrets.
- **Guest card tokens:** 128-bit random, SHA-256 hashed at rest, looked up by hash (no comparison timing to leak), rate-limited per client and per token prefix, retired hashes answer "reissued".
- **Webhooks:** WhatsApp Cloud verified with `X-Hub-Signature-256` over the raw body; Evolution/NextSMS/Africa's Talking with a constant-time shared secret; payments HMAC-verified over the raw body, applied atomically once per `provider_ref`, currency mismatches refused and audited.
- **Secrets at rest:** AES-256-GCM with a random 96-bit IV per value; provider settings shown only as `…last4`; no tokens, OTPs or phone numbers in API logs (route pattern logged, not path; `DEV_LOG_OTP` refused in production).
- **Web middleware (ADR 032):** redirects always target a fixed host built from `NEXT_PUBLIC_APP_DOMAIN`, never the request's `Host`; `next` redirects after login are limited to `/app` and `/ops` paths.
- **Docker:** multi-stage builds, non-root `node` user, health checks, only build outputs in runtime images; Postgres and Redis are not published to the host in `docker-compose.coolify.yml` and Redis requires a password.

## Prioritised recommendations

1. **H-01:** build staff TOTP before adding more staff accounts. Until it exists, remove the second-factor screen's implied guarantee from ADR 012 and the docs.
2. **M-03 then M-01:** fix client-IP derivation, then add per-client and global OTP limits with a cost alert.
3. **M-04 + M-05:** CSP (report-only first) and refresh tokens in `HttpOnly` cookies, staff first.
4. **M-06 and L-01:** atomic counters for gate PINs and refresh rotation (with client-side refresh serialisation).
5. **L-03, L-04, L-05, L-07, L-10:** small hardening items; add `pnpm audit --prod` and gitleaks to CI.
